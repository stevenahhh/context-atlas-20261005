01
THE MENTAL MODEL

분석 대상과 컨텍스트의 구분

이 하네스의 컨텍스트 관리를 설명하려면 ‘압축’이라는 말이 가리키는 작업부터 구분해야 한다. 한 작업은 저장 기록에서 이번 요청에 필요한 표현을 만드는 요청 투영이다. 다른 작업은 오래된 대화를 요약으로 대체해 활성 문맥을 재구성하는 compaction이다. 두 작업은 줄이는 대상뿐 아니라 실행 시점과 결과가 유지되는 범위도 다르다.[01]

이 구분은 하네스 효율의 세 축과 대응한다. 요청 투영과 compaction은 모델에 보내는 토큰의 양을 결정한다. 요청 사이에 앞부분을 얼마나 그대로 유지하느냐는 그 토큰에 적용되는 단가를 결정한다. 07절의 프롬프트 캐시가 이 축을 다룬다. 요약을 언제 만들고 언제 적용하느냐는 사용자가 기다리는 시간을 결정하며 05절의 주제이다. 세 축은 독립적이지 않다. 요청을 줄이는 변환이 앞부분을 바꾸면 단가가 오른다. 요약을 미리 만들어도 적용하지 못하면 대기 시간은 그대로이면서 생성 비용만 남는다.

REQUEST PROJECTION

모델 호출 단위의 정보 축소

context 훅은 세션 메시지를 복제한 뒤 그 복사본에 변환을 적용한다. 이 과정에서 큰 도구 출력의 중간 부분을 생략하거나, 오래된 답변의 앞부분만 남기거나, 본문을 작업 라벨로 바꾼다. 변환 결과는 해당 provider 요청의 입력이며 저장된 원본 메시지를 수정하는 결과물이 아니다.

이 작업에는 별도의 LLM 요약 호출이 필요하지 않다. 다만 문자열 처리와 토큰 추정에 드는 실행 비용은 존재한다. 정보 보존의 관점에서도 원본이 남는다는 사실과 모델이 그 내용을 볼 수 있다는 사실은 별개이다. 요청에서 빠진 내용을 다시 활용하려면 재조회 등 다른 경로가 필요할 수 있다.

APPLIED COMPACTION

요약에 의한 활성 문맥 재구성

Compaction은 오래된 대화 구간을 요약하고 그 결과를 보존할 최근 메시지와 함께 이후 요청의 바탕으로 사용한다. 요약의 적용은 한 번의 요청에만 영향을 주는 투영과 달리, 후속 대화가 참조하는 활성 문맥의 구성을 바꾼다.

요약 생성에는 대개 모델 요청이 든다. 백그라운드에서 미리 만들었다는 이유만으로 그 비용이 사라지는 것은 아니다. 생성과 적용 사이에 대화 상태가 바뀌어 결과를 사용하지 못한다면, 생성 비용은 지출했지만 활성 문맥을 줄이는 효과는 얻지 못할 수 있다.

예를 들어 긴 파일 조회 결과가 세션에 저장되어 있어도, 현재 요청에서는 그 자리에 [tool result cleared]만 들어갈 수 있다. 이때 파일을 조회했다는 대화 구조는 일부 남지만 모델은 해당 요청만으로 생략된 코드의 세부 내용을 확인할 수 없다. 요청량 감소를 평가할 때에는 이처럼 생략된 정보가 이후 작업에서 다시 필요해지는지도 함께 살펴야 한다.

이 보고서에서 provider는 모델 호출을 처리하는 제공자 또는 그 연결 구현을 가리킨다. Job은 백그라운드 요약 작업 하나를 뜻하며 warm 결과는 미리 생성해 두었으나 아직 적용하지 않은 요약을 말한다. 이러한 용어는 코드의 식별자와 대조할 수 있도록 원형을 유지하되, 생성 중인 작업과 완료된 결과를 구별해 사용한다.

정보 보존의 범위. 요청 축소는 세션 원본을 보존하는 손실 투영으로 해석하는 것이 적절하다. 기록의 보존은 확인되지만 모델에 전달되는 의미가 모두 보존되거나 필요한 정보를 항상 다시 찾을 수 있다는 보장까지 포함하지는 않는다.
02
EXECUTION ORDER

요청 처리 단계별 실행 순서

사용자의 요청 하나는 보통 여러 번의 모델 호출로 처리된다. 응답에 도구 호출이 포함되면 도구 실행 결과를 받은 모델이 다시 응답하는 과정이 이어질 수 있다. 이 하네스는 이 흐름의 여러 지점에 훅(hook)을 두고 새 사용자 요청을 시작할 때의 요약 판단과 각 모델 호출 직전의 요청 투영을 따로 수행한다. 이 구분은 어느 시점에 사용자 작업이 요약을 기다리게 되는지 설명하는 데 필요하다.[02]

  1. 새 요청 시작before_agent_start

    요약 필요성의 선행 판단

    판정에는 현재 사용량뿐 아니라 대기 중인 prompt와 이미지의 추정 토큰도 반영된다. 먼저 사용량과 reserve(나중을 위해 미리 떼어 두는 여유 토큰)의 합이 창에 도달하는 하드 리밋 조건을 확인한 다음, 적응 임계값과 유예 조건을 검사한다. 그보다 앞선 구간에서는 speculative 요약의 생성 조건을 확인한다. Blocking 경로를 선택하면 새 작업은 이 단계에서 요약을 기다릴 수 있다. 다만 조건에 도달했다는 사실만으로 적용이 확정되지는 않으며 breaker 상태와 provider별 소유권 등 추가 제약을 받는다.

    hard limit→threshold / grace→speculative start
  2. 각 모델 호출context

    Provider에 전달할 메시지의 구성

    요약 판단이 끝나면 실제 모델 요청을 만든다. 이때 도구 출력 admission, 일반 context reduction, emergency prune을 순서대로 적용한다. 뒤 단계는 앞 단계가 바꾼 메시지를 입력으로 받으므로, 같은 원문에 세 변환이 따로따로 적용되는 구조가 아니다. 이어서 provider별 replay 처리와 tool-call/result 짝 복구가 이어진다. 짝 복구는 일부 메시지가 사라진 뒤에도 요청에 필요한 호출과 결과의 짝을 정리하는 단계이다. 생략한 본문을 원문으로 되돌리는 작업은 아니다.

    admission→reduction→emergency→pair repair
  3. 응답·도구 실행message_end / turn_end

    응답 관찰과 복구 조건의 검사

    요약을 적용한 뒤에는 정해진 감시 구간에서 텍스트 없는 assistant 응답을 관찰한다. 감시기는 메시지 종류와 텍스트 존재 여부에 따라 연속 카운터를 갱신하므로, 도구 호출 횟수를 그대로 실패 횟수로 취급하지 않는다. 최근 요약의 절약량이 0인 경우에는 별도의 turn-end 복구 시도 경로도 존재한다. 여기서 사용하는 turn_end 횟수를 사용자의 요청 횟수와 동일하게 해석해서는 안 된다.

  4. 에이전트 종료agent_end

    유휴 시간의 요약 준비

    에이전트 작업이 끝난 뒤에는 다음 요청이 들어오기 전까지의 시간을 이용할 수 있다. 실행 모드와 설정, 중단·재시도 여부, breaker 상태가 적격하면 요약을 새로 시작하거나 기존 warm 결과를 유지한다. 생성 작업이 완료되더라도 세션이 여전히 유휴 상태이고 실제 요약 임계값 이상이어야 곧바로 적용할 수 있다. 사용자가 먼저 새 요청을 보내면 유휴 적용의 전제가 달라진다.

실행 순서의 해석. 요청 투영이 세 단계라는 사실만으로 “세 번 줄여 본 뒤에도 부족할 때 요약한다”고 설명할 수는 없다. 새 요청은 before_agent_start에서 먼저 blocking compaction을 기다릴 수 있다. 요청 축소 정책과 요약 실행 정책은 서로 영향을 주지만 하나의 직렬 축소 절차로 통합되어 있지는 않다.
03
DETERMINISTIC REDUCTION

결정적 규칙에 의한 요청 축소

아래 변환은 모델이 내용을 읽고 중요도를 판단하는 요약이 아니라, 메시지의 종류·위치·크기를 기준으로 수행하는 규칙 기반 처리이다. 설명의 범위는 이 하네스가 컨텍스트를 관리하고 관련 설정이 활성화된 기본 경로로 한정한다. SDK 소유 경로와 remote compaction 대상 모델의 예외는 뒤에서 별도로 다룬다. 각 수식의 토큰 값은 구현이 사용하는 추정량이며 문자열 길이와 UTF-8 바이트 수를 혼용해서는 안 된다.

5%ADMISSION

개별 도구 결과의 텍스트 예산 제한

Tool-admission은 도구 결과 하나가 요청 공간을 과도하게 차지하지 않도록 텍스트 예산을 제한한다. 전체 사용량과 무관하게 매 요청 실행된다. 다만 설정으로 비활성화할 수 있으므로 실행 여부는 설정에 달려 있다. 제한 대상은 도구 결과의 텍스트이며 이미지 부분을 이 예산에 맞춰 잘라내지는 않는다.[03]

cap = min(50,000, max(8192, floor(contextWindow × 0.05)))

기본 상한은 창의 5%를 기준으로 하되 8192토큰보다 작아지거나 50,000토큰보다 커지지 않도록 계산한다. 예를 들어 200k 창에서는 10,000토큰이 된다. 이 하한과 상한 때문에 작은 창과 큰 창에서는 실제 비율이 반드시 5%가 되지는 않는다.

출력이 예산을 넘으면 앞부분에 예산의 60%, 뒷부분에 20%를 배정해 발췌하고 생략 마커를 넣는다. 이는 원문 길이의 앞 60%와 뒤 20%를 보존하는 규칙이 아니다. 마커를 포함한 추정량이 여전히 초과되면 추가로 줄인다. 60%와 20%만으로 최종 요청량을 확정할 수는 없다.

50%REDUCTION GATE

오래된 대화와 도구 출력의 선택적 생략

일반 context-reduction은 사용량이 창의 절반 이상일 때 활성화된다. 이 단계에는 세 가지 변환이 포함되며 각각 보호하는 범위와 줄이는 대상이 다르다. 최근 정보를 보존한다는 목적은 공통이지만 보호 구간은 변환마다 따로 정의된다.[04]

연속 결과 접기는 오래된 구간에서 같은 종류의 read/search/shell 작업 쌍이 이어지는 경우 결과 본문을 그룹 라벨로 바꾼다. 기본적으로 최소 2개가 모여야 하며 최근 메시지 5개는 이 단계의 대상에서 보호한다. 여러 메시지를 하나로 합쳐 의미 요약문을 작성하는 것이 아니라, 개별 결과의 상세 본문을 작업을 나타내는 짧은 표현으로 치환하는 처리이다.

옛 답변 자르기는 최근 약 3000토큰의 보호 구간 밖에 있는 텍스트 전용 assistant 답변에 적용된다. 해당 답변이 800토큰을 넘으면 남길 본문의 목표를 800 × 0.3 = 240토큰으로 계산하고 축소 마커를 덧붙인다. 기준은 원문 길이가 아니라 설정된 800토큰이므로, 원문이 2000토큰이라고 해서 600토큰을 남기는 것은 아니다. 도구 호출 등이 섞인 메시지까지 같은 방식으로 처리한다고 일반화해서도 안 된다.

옛 도구 결과 비우기는 clearable 목록에 속한 도구 결과 중 최근 6개를 제외한 옛 텍스트를 마커로 바꾼다. 여기서 최근 6개는 clearable 도구 결과만 센 수이다. 앞선 변환에서 이미 발췌되거나 라벨로 바뀐 결과를 원문으로 되돌려 주지 않는다. 이 단계의 보호는 추가 삭제를 막는 범위에 그친다.

프롬프트 공간 초과에 대한 긴급 축소

Emergency-prune은 앞선 변환을 거친 뒤에도 메시지가 지나치게 큰 경우에 개입한다. 진입 조건은 메시지 추정량이 프롬프트용 창의 95%를 초과하는 것이며 이미 켜진 상태는 85% 이하가 되어야 해제된다. 두 판정의 분모는 모델의 전체 context window가 아니라 출력 공간을 제외한 프롬프트용 창이다.[05]

promptWindow = C − min(model.maxTokens, floor(C × 0.5))
engage: estimate > floor(promptWindow × 0.95)
release: estimate ≤ floor(promptWindow × 0.85)

유효한 양수 maxTokens가 주어지면 모델 출력 한도와 창의 절반 중 작은 값을 출력 reserve로 확보한다. 유효 값이 없으면 이 reserve를 빼지 않는다. 같은 전체 창 크기라도 모델의 출력 설정에 따라 긴급 축소의 절대 토큰 경계는 달라진다. 이는 뒤에서 설명하는 compaction reserve와 별개의 계산이다.

긴급 축소에서는 4096바이트를 넘는 도구 결과 텍스트 블록을 앞 800자와 뒤 400자로 잘라낸다. 길이 판정의 단위는 바이트이고 보존할 발췌의 단위는 문자이다. 도구 출력 예산이 여전히 초과되면 일부 블록은 생략 마커만 남도록 줄인다. 전체 메시지 추정량이 그래도 충분히 작아지지 않으면 오래된 메시지까지 제거한다. 마지막 단계는 본문 축소를 넘어 메시지 자체가 요청에서 빠질 수 있는 처리이다.

적응 임계값과 토큰 예산의 계산

요청 축소와 별도로, 이 하네스는 창 크기와 직전 요약의 절약률을 이용해 요약을 시작할 시점을 정하는 admission 임계값을 계산한다. 아래 실험은 기본 정책의 수식을 재현하며 실제 세션이나 모델을 호출하지 않는다. 입력 사용량에는 pending prompt의 추정량이 이미 포함되었다고 가정한다. 이 값과 도구 출력을 축소한 뒤 provider에 전달하는 요청량은 서로 다를 수 있다.[06]

Compaction reserve와 출력 reserve

Compaction reserve는 하드 리밋과 grace 등의 계산에 쓰인다. 기본 설정은 16,384토큰이다. Scaling이 활성화되면 창의 4%를 계산해 설정값과 비교하되, 창 크기로 계산하는 항은 최대 49,152토큰으로 제한한다. 설정값 자체가 그보다 크면 더 큰 설정값을 유지하므로 49,152를 모든 reserve의 절대 상한으로 읽어서는 안 된다.

R = max(configured,
min(floor(C × 0.04), 49,152))

출력 reserve는 emergency-prune에서 사용할 프롬프트 공간을 정한다. 이 계산에서는 모델의 maxTokens와 창의 절반 중 작은 값을 제외한다. 두 reserve는 목적과 입력값이 다르므로, 한쪽을 변경했을 때 다른 쪽 경계도 같은 양만큼 이동한다고 가정할 수 없다.

토큰 예산 리마인더는 모델의 행동을 조정하려는 별도 장치이다. 임계값까지 남은 양이 양수이고 lead의 두 배 이내이면, 같은 generation에서 한 번 남은 예산을 안내한다. 기본 200k 예시의 구간 시작점은 105,000토큰이다. 이 안내는 탐색과 답변을 간결하게 하도록 유도하지만 이후 모델이 소비할 토큰 수를 강제하는 제한이나 실제 절약량의 보장은 아니다.

수식과 실행 상태의 구분. 계산기는 경계의 위치와 명시한 job 조건에 따른 분기를 보여 준다. 실제 실행에는 요약 결과의 유효성, 세션의 유휴 여부, provider 소유권, 실패 상태가 추가로 관여한다. 이 실험의 분기 설명을 실시간 세션 관측 결과로 해석해서는 안 된다.

ASYNCHRONOUS COMPACTION

비동기 요약의 생성과 적용 조건

Speculative compaction은 요약을 필요로 할 가능성이 높은 시점에 먼저 생성 작업을 시작하는 정책이다. 목적은 생성 시간을 본래 작업이나 유휴 시간과 겹치게 하는 데 있다. 그러나 생성 중에도 대화가 진행될 수 있으므로, 완료한 요약이 현재 문맥에 적용 가능한지 다시 검증해야 한다. 이 때문에 생성 완료, 적용 가능, 실제 적용은 구별되는 상태이다.[07]

선행 생성의 시작점과 유예 구간

T = C × effectiveRatio
L = clamp(floor(T × 0.125), 8192, 32768)
start = max(0, T − L)
G = min(T + L, C − R)

T는 요약 임계값이고 L은 그보다 얼마나 앞서 생성을 시작할지 정하는 lead이다. 기본 lead는 임계값의 12.5%를 내림한 뒤 8192~32768토큰 범위로 제한한다. 사용자가 lead를 설정한 경우에는 비율 계산 대신 설정값을 사용하되 같은 범위를 적용한다. 기존 job이 있으면 새 작업을 중복해서 시작하지 않는다.

Grace band는 임계값에 도달한 뒤에도 미완성 job에 완료할 기회를 주는 유예 구간이다. Grace가 활성화되어 있고 입력량이 상한 G보다 작을 때 proactive blocking을 미룬다. 완료된 job에는 이 조건을 적용하지 않으며 하드 리밋 분기는 유예보다 먼저 검사한다. grace를 창의 한계까지 무조건 작업을 지속하도록 허용하는 기능으로 해석할 수는 없다.

유휴 생성과 유휴 적용의 분리

Idle warm-up은 에이전트 작업이 끝난 뒤 다음 요청을 기다리는 시간을 이용한다. 일반적인 warm 생성의 하한은 창의 50%이지만 완료한 요약을 유휴 상태에서 적용하려면 adaptive threshold 이상이라는 별도 조건을 만족해야 한다. 200k 기본값에서 100k에 생성한 결과가 완성되더라도 사용량이 140k 미만이면 보관될 수 있다.

유휴 경로는 TUI·RPC·app-server 같은 지속 모드와 enabled 설정을 확인하고 retry/abort 여부 및 breaker 상태의 제약을 받는다. 임계값에 이미 도달한 경우의 처리가 subthreshold warm 생성보다 먼저이므로, 작은 창에서는 50%보다 낮은 기본 임계값에서 작업을 시작할 수 있다. 완료 시점에도 같은 job의 결과이고 세션이 계속 유휴 상태인지 확인해야 한다.

비동기 결과의 유효성 검증에서는 generation과 revision을 구분한다. Generation은 결과가 속한 처리 세대를, revision은 메시지 상태의 변경을 구별하는 값이다. Generation이 달라진 결과는 적용하지 않는다. Revision이 달라졌더라도 요약의 기준 경계가 보존되었다면 anchor 검증을 통과할 수 있으므로, 단순히 새 메시지가 추가되었다는 이유만으로 모든 요약을 폐기하는 구조는 아니다.

Warm anchor의 검증 범위. 보존 경계가 존재하고 최신 compaction ID와 경계 앞의 entry ID 순서가 기준과 일치하면 뒤에 메시지가 추가되었어도 요약이 유효할 수 있다. 이는 본문 전체를 다시 해석하는 검증이 아니라 entry의 식별자와 경계를 확인하는 방식이다. 토큰 증가량 > max(keepRecent, 8192)은 유휴 job을 교체할지 판단하는 조건이며 blocking 소비를 포함한 모든 적용 경로에 공통으로 적용되는 폐기 상한은 아니다.
지연 감소의 한계. 다음 요청이 요약 완료보다 먼저 들어오면 blocking 경로가 미완성 작업을 기다릴 수 있다. 생성 실패나 상태 변경으로 결과를 폐기하는 경우도 가능하다. 선행 생성은 대기를 숨길 기회를 제공하지만 모든 요청에서 체감 지연이 0이 되거나 요약 비용이 줄어든다는 보장은 아니다.

BREADCRUMBS & FAILURE GUARDS

요약 이후의 단서 복원과 실패 관리

요약으로 오래된 문맥을 대체하면, 후속 작업에서 참조해야 할 파일이나 사용하던 스킬에 대한 단서도 약해질 수 있다. 이 하네스는 이를 보완하는 restoration tracker와 요약 실행의 실패를 제한하는 장치를 둔다. 다만 복원하는 정보의 내용, 실패로 집계하는 사건, 복구 시도의 허용 범위는 서로 다른 구현에 속하므로 하나의 자동 복구 기능으로 묶어 설명하기 어렵다.

복원 대상과 항목 선택 기준

Restoration tracker는 도구 호출의 입력에서 파일 경로·작업 종류·스킬 이름을 기록한다. 예를 들어 파일 항목의 내용은 src/foo.ts (read, edit)와 같은 라벨이다. 파일을 다시 읽어 본문을 넣거나 스킬의 지침을 다시 로드하는 처리는 포함하지 않는다. 도구의 실행 성공을 확인한 뒤 그 결과물을 보존하는 구조도 아니므로, 라벨의 존재를 해당 작업이 성공했다는 증거로 해석해서는 안 된다.[08]

요약이 수용되면 복원할 내용을 대기 상태로 두고 다음 before_agent_start에서 한 번 소비한다. 선택 순서는 최근순이 아니라 우선순위, 짧은 항목, 이름순이다. ‘최근에 읽은 파일을 그대로 되살린다’는 표현은 정보의 내용과 선택 기준 양쪽에서 구현과 어긋난다. 기능의 범위는 후속 작업에 관련된 대상을 상기시키는 것으로 보는 편이 정확하다.

실패 누적에 따른 실행 중단

Circuit breaker는 실패가 반복되는 동안 자동 압축을 잠시 멈추는 장치이다. 기록된 연속 실패가 3회에 도달하면 60초의 cooldown을 두고 성공이 기록되면 실패 횟수를 초기화한다. 수동 압축은 이 중단을 우회할 수 있다.[09]

여기서 기준은 ‘기록된 실패’이다. speculative 생성 오류는 그 자체로는 job의 오류 상태로만 남는다. 카운터에 들어가는 것은 blocking 경로가 이를 이어받아 일시적 실패로 기록한 경우이다. 실패 집계는 이벤트 소유권과 실행 경로에 따라 달라진다. Cooldown 중에는 임계값 이상의 요청에서 결정적 축소를 활용하는 경로가 있으며 이 하네스의 긴급 축소 경로도 남아 있다.

<10%OR <1024 TOKENS

비효율 요약의 집계 범위

절약량이 1024토큰 미만이거나 절약률이 10% 미만이면 ineffective로 집계한다. 그러나 현재 shouldRejectByCap()은 항상 허용하는 결과를 반환한다. 비효율 카운트가 이후 압축을 차단하는 실행 제한으로 사용되지는 않는다.

수용된 요약은 이 집계에 앞서 성공으로 기록되어 breaker의 실패 횟수를 초기화한다. 따라서 비효율 카운트가 circuit breaker를 직접 작동시킨다고 설명할 수 없다. 절약률에 따른 임계값 조정, 비효율의 기록, 실패에 따른 cooldown은 연결 관계를 각각 확인해야 하는 별도 정책이다.

요약이 수용되면 5번의 turn_end 동안 감시 구간을 연다. 이 구간에서 텍스트 없는 assistant 메시지의 연속 카운터가 3에 도달하면 복구 압축을 시도한다. 텍스트가 있거나 감시 대상 비-assistant 메시지가 들어오면 연속 카운터를 초기화한다.[10]

복구는 한 사이클에 한 번 시도하며 여러 사이클을 통틀어 최대 3회의 제한이 있다. 시도 횟수는 복구가 수용되기 전에 증가하므로 거절된 시도도 한도를 소비할 수 있다. Breaker 등 다른 실행 제약도 받기 때문에 발동 조건을 만족했다는 사실이 복구 완료를 의미하지는 않는다.

도구 사용과 응답 저하의 구별. Assistant의 tool-only 메시지 사이에 tool result가 들어오면 연속 카운터가 초기화될 수 있다. 이 감시기는 텍스트 답변 없이 도구를 사용한 횟수 자체를 세지 않는다. 조건 평가의 입력은 assistant 응답만이 아니라 그 사이에 발생한 메시지 이벤트를 포함한다.

두 수치는 분모의 구성이 다르므로 서로 비교해 정책의 효과를 판단할 수 없다. 특정 시점의 캐시 붕괴는 footer 값에, 세션 전체의 과금 구조는 누적값에 나타난다. 세션 정보 화면은 이와 별도로 cache waste를 계산해 직전 요청에 있었으나 캐시에서 읽지 못한 토큰을 집계한다.

캐시가 깨지는 지점과 감지

cache-stats.ts는 assistant 메시지마다 직전 요청과 비교해 miss를 계산한다. 직전 prompt 토큰과 현재 prompt 토큰 중 작은 값에서 cacheRead를 뺀 값이 1024토큰을 넘으면 miss로 집계한다. 이때 직전 요청 이후 경과 시간과 모델 변경 여부를 함께 기록한다. 경과 시간이 5분을 넘으면 TTL 만료를 원인 후보로 표시한다. 캐시 활동을 한 번도 보고하지 않은 provider에서는 miss를 세지 않는다.

missedTokens = min(prevPromptTokens, promptTokens) − cacheRead
counted if missedTokens > 1024

구현에서 확인되는 prefix 변경 원인은 다음과 같다. 압축 적용은 활성 문맥을 통째로 바꾸므로 그 직후 호출은 새 내용으로 취급되어 miss 집계에서 제외된다. 모델 전환은 전체 prompt를 다시 과금하므로 miss로 센다. 앞 절의 축소 정책에서는 50% gate를 처음 넘는 순간, clearable 도구 결과의 최근 6개 창이 밀리는 순간, emergency latch가 켜지는 순간에 prefix 중간이 바뀐다. system prompt에는 Current date가 포함되므로 날짜가 바뀐 뒤 prompt를 다시 조립하면 system 블록의 캐시도 새로 쓰인다.

정책과 적중률의 관계. 높은 적중률은 체크포인트 배치와 큰 고정 prefix가 만든다. 컨텍스트 정책은 그 prefix를 불필요하게 바꾸지 않도록 설계되어 있다. 정책이 적중률을 생성한다고 서술하면 인과가 뒤바뀐다. 정책의 효과를 보려면 세션 평균이 아니라 압축 직후와 축소 단계 전환 직후 호출의 footer 값과 cache waste를 봐야 한다.

OpenAI remote 대상일반 reduction을 기본적으로 제외한다. 이 하네스 관리 경로의 admission과 emergency는 유지한다.Pre-turn speculative와 임계값 미만의 idle warm은 제외한다. 임계값 이상의 local idle 경로는 유지한다.Blocking/core 경로는 remote compaction을 먼저 시도한다. 대상 판정에 해당하는 모델에 한정된다.
resident Claude SDKSDK가 컨텍스트를 소유하면 이 하네스의 축소 파이프라인은 적용하지 않는다.이 하네스의 자동 압축과 degradation 감시도 물러난다.resumeMode: off 또는 compaction 모델 override가 소유권을 바꿀 수 있다. 수동 압축은 별도 경로이다.

표는 모든 분기를 열거한 상태 전이표가 아니라 주요 경로의 기본 구분이다. Breaker fallback 같은 조건은 일반 reduction gate를 별도로 우회할 수 있다. 각 enabled 플래그의 검사 위치가 같지 않으므로, 하나의 설정으로 모든 선행·유휴 경로가 대칭적으로 제어된다고 가정해서는 안 된다.

특히 OpenAI remote 대상이라는 표현을 모든 OpenAI 모델과 동일시하면 적용 범위를 잘못 판단하게 된다. 마찬가지로 resident Claude SDK의 기본 동작만 보고 이 하네스가 해당 provider에서 어떤 압축도 수행하지 않는다고 결론 내릴 수는 없다. 소유권을 바꾸는 설정과 수동 실행 경로가 있기 때문이다. 실제 세션의 정책은 모델 이름이 아니라 연결 방식과 compaction 설정의 조합으로 결정된다.

Codex와 Claude Code의 자동 요약은 도달한 턴에 즉시 동기 실행되므로 그 호출이 늦어지는데, 이 하네스는 임계값 앞 lead와 유휴 시간에서 미리 생성해 둔다. 셋째, 실패 관리다. 요약 실패의 circuit breaker와 무텍스트 응답 감시에 해당하는 장치는 두 구현체에서 확인되지 않았다.

Claude Code는 요약 이후 CLAUDE.md·메모리·최근 수정 파일 5개·스킬 본문을 디스크에서 다시 읽어 붙이는 복원 단계가 문서에 명시되어 있고 서버 측 context editing은 클라이언트 구현 없이 같은 효과를 낸다. 이 하네스의 restoration tracker가 라벨만 재주입해 세부 본문 복원은 하지 않는 대조점이다.

비교의 비대칭. Codex는 소스 전체를 읽을 수 있으므로 각 셀이 코드 확인 값이고 Claude Code는 문서와 usage 관측이 근거다. "문서에 없음"은 "구현에 없음"이 아니며 Claude Code 행의 부재 표시는 모두 관측 범위 한정으로 읽어야 한다.[20]

기존 설명에 대한 구현 기반 정정

기존 설명은 요청 축소와 선행 요약을 결합한 다층 구조를 대체로 올바르게 파악했다. 다만 일부 수치의 기준을 바꾸어 읽거나 특정 경로의 조건을 전체 정책의 보장으로 확대했다. 아래 항목은 결론에 영향을 주는 차이를 정리한 목록이다. ‘정정’은 구현과 다른 내용이며 ‘조건부’는 적용 범위나 추가 조건을 명시해야 성립하는 설명이다.

정정“파일·스킬 본문을 복원해 재독을 줄인다”

Restoration tracker가 재주입하는 것은 파일 경로·작업 종류·스킬 이름이다. 본문을 다시 읽거나 스킬 지침을 로드하는 기능은 포함하지 않는다. 항목 선택도 최근순이 아니라 우선순위, 짧은 항목, 이름순으로 이루어진다.

관련 대상을 상기시키는 효과는 기대할 수 있지만 그 단서만으로 후속 작업에 필요한 본문을 확보했다고 볼 수는 없다. 파일 재독 횟수나 비용이 줄었다는 결론은 별도의 실행 관찰이 필요하다. 근거 [08]

정정“800토큰 넘는 옛 답변을 원문의 30%로 축소한다”

남길 본문의 목표는 설정 기준 800토큰의 30%, 약 240토큰이다. 원문이 2000토큰이어도 600토큰을 남기는 계산이 아니며 최종 결과에는 축소 마커가 추가된다.

적용 범위도 최근 보호 구간 밖의 텍스트 전용 assistant 메시지로 제한된다. 축소 비율만 전달하고 이 조건을 생략하면 최근 답변이나 도구 호출이 포함된 메시지에도 같은 처리가 적용되는 것으로 오해할 수 있다. 근거 [04]

정정“비효율 요약을 circuit breaker가 걸러낸다”

Ineffective 카운터와 실패 breaker는 현재 직접 연결되어 있지 않다. 수용된 요약은 먼저 성공으로 기록되어 실패 횟수를 초기화하며 비효율은 별도 카운트와 로그로 남는다. Cap 판정도 항상 허용하는 값을 반환한다.

따라서 주석에 나타난 차단 의도를 현재 실행 코드의 보장으로 인용할 수 없다. 실패를 반복한 작업의 cooldown과 성공했지만 절약량이 작은 요약의 집계는 서로 다른 장치이다. 근거 [09]

조건부“50%에서 idle 요약을 만들고 바로 적용한다”

창의 50%는 일반적인 유휴 warm 생성의 하한이다. 완료 후 idle apply에는 adaptive threshold 이상이라는 별도 조건이 있고 세션이 계속 유휴 상태인지도 확인한다. 기본 200k 예시에서는 100k에서 생성했더라도 140k 미만이면 결과를 보관할 수 있다.

사용자가 생성 완료 전에 새 요청을 보내면 유휴 적용의 전제가 사라지는 경우도 있다. Blocking 경로가 미완성 job을 기다리는 경우도 있으므로, 이 정책에서 무지연을 보장한다고 결론 낼 수는 없다. 근거 [07]

조건부“max(keepRecent, 8192)만큼 자라면 결과를 폐기한다”

시작 이후 토큰 증가량이 해당 값을 초과하는지 검사하는 조건은 유휴 warm job의 교체 판단에 쓰인다. 값에 도달한 경우와 초과한 경우를 구분해야 하며 시간 경과에 의한 만료 조건도 아니다.

Blocking 소비 등 다른 경로는 generation, revision, anchor의 유효성을 확인한다. 토큰 증가량 공식을 모든 적용 경로에 공통인 폐기 제한으로 설명하면 실제로 유효한 결과의 처리까지 잘못 예측하게 된다. 근거 [07]

조건부“히스토리 손실 없이, 항상 더 싸고 빠르다”

저장 원본의 보존과 요청 정보의 보존은 다르다. 이번 모델 요청에서 생략한 본문은 모델 입력에 포함되지 않는다. 발췌와 마커가 필요한 정보를 충분히 유지했는지는 작업에 따라 달라질 수 있다.

실제 비용을 평가하려면 요청량 감소뿐 아니라 요약 생성과 폐기, provider 캐시 적중, 생략한 정보의 재탐색도 함께 관찰해야 한다. 본 보고서는 실행 조건을 분석한 자료이며 비용이나 지연의 실측 결과를 포함하지 않는다.

조건부“이 하네스는 compaction을 더 늦게 한다”

직전 yield 조정이 없는 기본 200k 창에서 이 하네스의 요약 admission 임계값은 140,000토큰이다. 비교한 upstream pi의 기본 조건은 183,616토큰 초과이므로, 이 하네스는 이 기준에서 요약을 더 일찍 고려한다.

다만 이 비교는 admission 기준의 비교이다. 이 하네스의 생성 시작점은 그보다 앞설 수 있고 미완성 job에 대한 grace는 blocking을 늦출 수 있다. 생성, 적용, blocking의 시점을 분리해야 두 시스템을 같은 기준으로 비교할 수 있다. 근거 [12]

분석 근거와 결론의 범위

보내는 토큰을 줄이고 보낸 토큰을 캐시 단가로 받으며
요약 대기를 작업 시간과 겹친다.
세 축의 실제 절감 효과는 별도 측정이 필요하다.

효율적인 에이전트 하네스라는 관점에서 이 구현은 세 가지 변수를 각각 다른 장치로 다룬다. 요청량은 admission, reduction, emergency prune과 compaction이 줄인다. 과금 단가는 provider별 캐시 표시와 세션 키, TTL을 넘기지 않는 대기 예산, 요청 형태를 안정시키는 히스테리시스가 관리한다. 대기 시간은 speculative 생성, grace band, 유휴 warm-up이 줄이려 한다. 세 축은 서로 영향을 준다. 예를 들어 압축은 요청량을 줄이지만 그 직후 호출의 캐시를 비운다. 축소 단계의 전환도 요청량을 줄이면서 prefix를 바꾼다. 어느 한 축의 지표만으로는 하네스의 효율을 판단할 수 없다.

분석 기준 커밋은 f81aee565f2aeb6d774c93801596e523c017c4c5이다. 정책 디렉터리에는 TypeScript 파일 47개, 8537줄이 있으며 해당 경로의 2026-04-27 이후 이력은 216커밋으로 확인했다. 이러한 수치는 정책 구현의 범위와 변경 이력을 보여 주지만 압축 품질이나 실행 효율을 입증하는 지표로 사용할 수는 없다.

분석에서는 정책 함수의 조건과 반환값을 읽고 실제 이벤트 훅과 호출부에서 그 값이 어떻게 소비되는지 대조했다. 관련 테스트는 기대 동작을 확인하는 보조 근거로 읽었다. 특히 함수나 주석의 이름이 암시하는 기능을 그대로 채택하지 않고 실행 경로가 그 기능을 실제로 강제하는지 확인했다. 비효율 집계와 breaker의 비연결, 유휴 생성과 적용 조건의 차이는 이 대조에서 드러난 사례이다.

원본 코드의 테스트 실행, 실제 모델 요약 호출, cache hit·지연·비용 벤치마크는 수행하지 않았다. 보고서의 대화형 시각화는 명시된 가정 아래 공식과 상태 판정을 재현하는 설명 도구이다. 수식을 재현했다는 사실만으로 특정 작업에서 요약 품질이 유지되거나 총비용이 감소한다고 결론 내릴 수는 없다.

이 구현은 요청에 포함되는 정보를 규칙적으로 줄이는 방향과, 요약이 필요해지기 전에 생성을 시작해 대기의 일부를 다른 작업 시간과 겹치는 방향으로 설계되어 있다. 그 과정에서 원본 기록은 유지되지만 현재 요청의 정보는 생략된다. 선행 생성한 결과를 사용하지 못할 가능성도 남는다. 실제 효과를 평가하는 후속 검증에서는 줄어든 요청량과 함께 요약 요청 수, 폐기된 결과, 재탐색, 사용자 대기 시간을 같은 작업 조건에서 관찰해야 한다. 이는 향후 측정의 기준이며 본 보고서가 확보한 실측 결과는 아니다.
